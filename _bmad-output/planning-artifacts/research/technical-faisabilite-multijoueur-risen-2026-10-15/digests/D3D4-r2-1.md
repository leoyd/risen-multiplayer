# D3D4-r2-1: GCC ABI bugs, llvm-mingw sret, and D3D9 hooking under DXVK (round 2)

Note: gcc.gnu.org/bugzilla was blocked (Anubis bot-protection, "Access Denied") for both PR 64384 and PR 52792. winehq pipermail returned 404/403. Bug status therefore comes only from mailing-list mirrors and search snippets.

## Findings
- claim: GCC PR target/64384 has the title "mingw-w64: stdcall function returning an aggregate is incompatible with MS ABI". A June 2020 comment says it still reproduces in GCC 10.1, using D3D12 GetCPUDescriptorHandleForHeapStart (8-byte struct return) as the example. - claim: Wine commit (wine-cvs, July 2017): MSVC passes the hidden aggregate-return pointer right after `this`, while g++ (at least through 6.3) passes it before `this`. Wine's widl workaround declares the return pointer as an explicit parameter in the vtable entry and adds an inline wrapper for source compatibility. This affects 64-bit Winelib and possibly mingw-w64 users of Wine headers. | source: https://www.winehq.org/pipermail/wine-cvs/2017-July/122239.html (seen through a search snippet only; the direct fetch returned 403) | publisher: WineHQ | pub_date: 2017-07 | accessed: 2026-10-15 | confidence: medium | class: pattern
- claim: Josh Staiger's C-side workaround for the same D3D12 method: declare the vtable slot so the struct comes back through an explicit output pointer instead of a return value. Without that, the returned handle is wrong and CreateRenderTargetView crashes later. | source: https://joshstaiger.org/notes/C-Language-Problems-in-Direct3D-12-GetCPUDescriptorHandleForHeapStart.html | publisher: Josh Staiger (blog) | pub_date: ~2020 | accessed: 2026-10-15 | confidence: medium | class: pattern
- claim: Clang in MS-ABI mode passes sret after `this` for instance methods (D3618, 2014; "MSVC always passes 'sret' after 'this', unlike GCC"). Clang's MS-ABI test also states that instance methods compiled by MSVC never return records in registers and always use a hidden sret pointer placed after `this`. | source: https://reviews.llvm.org/D3618?id=9092 ; https://llvm.googlesource.com/clang/+/e0d57a1cf3318352fa3fd7253c744f3f4e079c17 ; https://llvm.googlesource.com/clang/+/master/test/CodeGenCXX/thiscall-struct-return.cpp | publisher: LLVM | pub_date: 2013–2014 | accessed: 2026-10-15 | confidence: high (for the clang-cl / *-windows-msvc target) | class: version-compat
- claim: I found no source saying that llvm-mingw (x86_64-w64-windows-gnu, Itanium C++ ABI) applies the MSVC member-function sret rule. My unverified belief is that it behaves like GCC, because the rule lives in the MS C++ ABI code path. Practical implication: only clang-cl / --target=x86_64-pc-windows-msvc (for example with xwin) is MSVC-exact for C++ member calls. With MinGW toolchains (GCC or clang), declare struct-returning member functions as free functions `void(*)(This*, Ret*, args...)` with an explicit out-pointer, as Wine does. | source: inference from the LLVM sources above | publisher: n/a | pub_date: n/a | accessed: 2026-10-15 | confidence: low | class: version-compat

## Leads worth chasing
- Retrieve the GCC Bugzilla entries for PR 64384 and PR 52792 with a real browser (Anubis blocks bots) to check the status field and the last comments.
- The widl-generated d3d12.h in mingw-w64-headers: check how WIDL_EXPLICIT_AGGREGATE_RETURNS or the explicit-return-pointer vtable form is emitted today. That is the canonical MinGW workaround.
- Test empirically: compile a one-line `struct S{int a,b;}; S (*fn)(void*)` call with x86_64-w64-mingw32-g++ and with clang --target=x86_64-w64-windows-gnu, then compare the disassembly against MSVC (godbolt). This settles the question in about 10 minutes.
- DXVK PRs #5846 and #5851 show what overlay hook patterns DXVK accommodates. Search the DXVK issues for "overlay" or "hook" with the d3d9 label.
- Look for a DXVK + MinHook/ImGui DX9 success report, for example from trainers or the Steam overlay. The Steam overlay itself hooks D3D9 under Proton, which would be indirect evidence that hooking works.

## Looked for but not found
- Any GCC release note or commit that fixes PR 64384 or PR 52792 (none found; status unverified).
- Any clang flag or attribute that makes the MinGW target use MSVC member-function sret ordering (none found).
- Explicit confirmation that llvm-mingw matches GCC (rather than MSVC) for member aggregate returns.
- A primary-source report (DXVK issue, ImGui issue, ReShade forum) confirming that EndScene/Present vtable hooking works, or breaks, on DXVK d3d9 under Proton. Nothing specific turned up. No evidence of vtable incompatibility either: DXVK's d3d9 objects are COM interfaces, and COM vtable layout is ABI-stable across compilers (my belief; not retrieved this run).
