# Digest D4/D5 (r1-3): MSVC ABI toolchain from Linux and transport

Researched 2026-10-15. All claims below come from sources retrieved during this run.

## D4 Findings

- claim: On MSVC x64, user-defined types are returned in RAX only from global functions and static member functions, and only if they are POD-like and 1/2/4/8/16/32/64 bits in size. In every other case the caller allocates the return buffer and passes a hidden pointer, which the callee returns in RAX. The doc's own wording limits register return to "global functions and static member functions", which implies that non-static member functions always use the hidden pointer. | source: https://learn.microsoft.com/en-us/cpp/build/x64-calling-convention | publisher: Microsoft Learn | pub_date: 2025-03-19 (updated 2026-05-21) | accessed: 2026-10-15 | confidence: high | class: version-compat
- claim: The basic MSVC x64 convention is RCX/RDX/R8/R9 plus XMM0-3, a 32-byte shadow space, and aggregates that are not 1/2/4/8 bytes passed by pointer. `this` is just the first integer argument. Function pointers are plain code addresses, so a non-virtual exported method can be called through a function pointer whose type is `Ret(*)(Class* self, args...)`, as long as the return is scalar. | source: https://learn.microsoft.com/en-us/cpp/build/x64-calling-convention | publisher: Microsoft Learn | pub_date: 2025-03-19 | accessed: 2026-10-15 | confidence: high | class: pattern
- claim: For instance methods, MSVC always puts the hidden sret pointer after the implicit `this` (RCX=this, RDX=sret). LLVM had to change its backend so it no longer assumes sret comes first. | source: https://reviews.llvm.org/D3617 (seen as a search snippet only, not fetched) | publisher: LLVM Phabricator | pub_date: unknown (~2014) | accessed: 2026-10-15 | confidence: medium | class: version-compat
- claim: Microsoft's MIDL docs say C++ member functions that return structs take a hidden return-buffer pointer as the second parameter, after `this`, and return that pointer. | source: https://learn.microsoft.com/en-us/windows/win32/midl/-cstruct-out (search snippet) | publisher: Microsoft Learn | pub_date: unknown | accessed: 2026-10-15 | confidence: medium | class: version-compat
- claim: GCC/mingw-w64 x86_64 is still incompatible with MSVC for member functions returning aggregates (GCC bug 64384). Example: a D3D12 method returning an 8-byte struct, where GCC expects RAX but the MSVC DLL writes through a hidden pointer in RDX. Still reported broken in GCC 10.1 (comment dated 2020-06-15). I did not find evidence of a fix (Bugzilla blocked the fetch). | source: https://gcc.gnu.org/pipermail/gcc-bugs/2020-June/705246.html | publisher: GCC bugs mailing list | pub_date: 2020-06-15 | accessed: 2026-10-15 | confidence: medium (fix status unverified) | class: failure
- claim: Wine documents that g++ (at least up to 6.3) puts the implicit return pointer before `this` even with ms_abi, and works around it with explicit aggregate-return handling in widl (DWIDL_EXPLICIT_AGGREGATE_RETURNS). The related GCC bug is 52792. | source: https://www.winehq.org/pipermail/wine-cvs/2017-July/122239.html (search snippet) | publisher: WineHQ | pub_date: 2017-07 | accessed: 2026-10-15 | confidence: medium | class: failure
- claim (derived): With MinGW g++, calling MSVC methods is safe only when (a) they return scalar, pointer or void, or (b) the developer writes the ABI by hand: declare the call as a free function `Ret* fn(Class* self, Ret* out, args...)`. This trick works under either compiler because a pointer return goes in RAX. Using real C++ member-function pointers or vtable calls from GCC is not safe. | source: inferred from the three sources above | confidence: medium | class: pattern
- claim: clang-cl + lld-link work from Linux with the MSVC CRT and SDK. LLVM ships an official CMake toolchain file, `llvm/cmake/platforms/WinMsvc.cmake`: clang-cl as CC/CXX, lld-link as linker, llvm-lib as archiver, and an MSVC/SDK version passed in. | source: https://llvm.googlesource.com/llvm-project/llvm/+/refs/heads/main/cmake/platforms/WinMsvc.cmake | publisher: LLVM | pub_date: main branch (undated) | accessed: 2026-10-15 | confidence: high | class: landscape

## D5 Findings

- claim: KCP (skywind3000) is only a pure ARQ algorithm: ikcp.h/ikcp.c, no syscalls, with UDP I/O and the clock supplied by the caller through an output callback, `ikcp_input` and `ikcp_update`. It has no connection or session management (projects like asio-kcp add that) and no unreliable channel. Both peers must use the same `conv`. Recommended fast mode is `ikcp_nodelay(kcp,1,10,2,1)`, optionally with `rx_minrto=10`. | source: https://github.com/skywind3000/kcp | publisher: skywind3000 | pub_date: unknown (no release dates visible) | accessed: 2026-10-15 | confidence: high | class: pattern
- claim: xtaci/kcp-go is actively maintained. Latest tags: v5.6.72 (2026-03-27), v5.6.71 (2026-03-13), v5.6.70 (2026-02-10). It claims compatibility with skywind3000's C KCP. | source: https://github.com/xtaci/kcp-go/tags | publisher: xtaci | pub_date: 2026-03-27 | accessed: 2026-10-15 | confidence: high | class: status
- claim: kcp-go's `Dial`/`Listen` default to `block=nil, dataShards=0, parityShards=0`, which means no encryption and no FEC. In that case headerSize=0 and the wire format is a raw KCP segment (conv u32 first), so it interoperates with plain ikcp. With `*WithOptions` plus crypt, a 16-byte nonce and 4-byte CRC32 are prepended (or the AEAD nonce). FEC adds its own header (seqid, type 0xF1/0xF2, size). Either one breaks raw-ikcp interop unless the C side implements it too. | source: https://raw.githubusercontent.com/xtaci/kcp-go/master/sess.go , https://github.com/xtaci/kcp-go | publisher: xtaci | pub_date: master as of 2026-10-15 | accessed: 2026-10-15 | confidence: high | class: version-compat
- claim: The kcp-go Listener keys sessions by remote address and takes `conv` from the first packet. On a conv mismatch it drops packets, unless sn==0, which resets the session. KCP has no SYN/FIN/RST, so the application must supply keepalive or heartbeat (kcp-go suggests smux). Without encryption, headers are plaintext and can be tampered with. | source: https://raw.githubusercontent.com/xtaci/kcp-go/master/sess.go , https://github.com/xtaci/kcp-go | publisher: xtaci | pub_date: 2026 | accessed: 2026-10-15 | confidence: high | class: failure
- claim (derived): To get unreliable state packets on the same socket as KCP, the project needs its own 1-byte channel prefix (or a separate port), demultiplexed before `ikcp_input`. kcp-go's Listener would treat any non-KCP datagram as KCP (the first 4 bytes read as conv). So the Go server should either read raw UDP itself and drive kcp-go's lower-level KCP object, or use a separate socket for unreliable traffic. | source: inferred from sess.go behavior above | confidence: medium | class: pattern
- claim: Valve GameNetworkingSockets supports reliable and unreliable messages, has a plain C interface for bindings, and does P2P NAT traversal through WebRTC ICE. Third-party Go bindings exist (nielsAD/gns). | source: https://github.com/ValveSoftware/GameNetworkingSockets | publisher: Valve | pub_date: unknown (no release date visible) | accessed: 2026-10-15 | confidence: medium | class: landscape
- claim: ENet's Go options are cgo bindings (codecat/go-enet, which needs system libenet and a C compiler) or genet, a pure-Go ENet aiming at C wire compatibility that is explicitly experimental and not production-ready (published 2026-05-18, C<->Go interop still "next focus"). | source: https://pkg.go.dev/github.com/codecat/go-enet , https://pkg.go.dev/github.com/SeanTolstoyevski/genet | publisher: pkg.go.dev | pub_date: genet 2026-05-18 | accessed: 2026-10-15 | confidence: medium | class: landscape
- claim: netcode (mas-bandwidth, Glenn Fiedler) is C with BSD-3. It provides connection slots, timeouts, libsodium encryption and signing, connect tokens issued by a web backend, and replay/amplification protection. It carries only unreliable, unordered packets; reliability is a separate library (reliable, yojimbo). A Go port exists (wirepair/netcode). Recency was not determinable from the page. | source: https://github.com/mas-bandwidth/netcode | publisher: Más Bandwidth | pub_date: unknown | accessed: 2026-10-15 | confidence: medium | class: landscape
- claim: Snapshot interpolation pattern: buffer snapshots and render in the past, with a delay of about 3x the send interval plus jitter margin (10 Hz ≈ 350 ms, 30 Hz ≈ 150 ms, 60 Hz ≈ 85 ms) so that two consecutive lost packets can be survived. Never wait for a resend. Extrapolation is acceptable only for short, near-linear motion (about 50-250 ms). Hermite splines (using velocity) beat linear interpolation, and slerp is enough for rotation. | source: https://gafferongames.com/post/snapshot_interpolation/ | publisher: Glenn Fiedler (Gaffer On Games) | pub_date: 2014-11-30 (classic reference) | accessed: 2026-10-15 | confidence: high | class: pattern
